# Mac에서 스내치 분석 API 실행하기

측면 MP4 한 편을 제출하면 분석이 끝날 때까지 기다렸다가 원판 추적 요약과 결과 링크를 받습니다. 영상 전송, 추론, 결과 저장은 같은 Mac에서 실행합니다.

Docker Desktop에서 CPU 버전을 실행하는 방법과 같은 영상으로 대조한 결과는 [CPU Docker 검증](cpu_docker.md)에 정리했습니다.

## 서버 시작

프로젝트 루트에서 실행합니다. 처음에는 개발 의존성까지 설치합니다. Python 3.12, uv, ffprobe와 베이스라인 원판·CutMix 원판·자세 가중치가 필요합니다. [모델 위치와 MP4 준비 방법](analyze_mp4.md)을 참고하세요.

```bash
uv sync --locked --inexact
cp -n .env.example .env
```

VS Code에서 이 프로젝트 폴더를 열고 새 터미널에서 실행합니다.

```bash
source .venv/bin/activate
fastapi dev
```

가상환경이 이미 켜져 있으면 `fastapi dev`만 입력합니다. 프로젝트의 `.env`를 읽고 서버가 준비되면 기본 브라우저에 [Swagger 문서](http://127.0.0.1:8000/docs)가 한 번 열립니다. 코드를 저장하면 서버가 자동으로 다시 로드됩니다. 종료할 때는 같은 터미널에서 `Ctrl+C`를 누릅니다.

기본 추론 장치는 CPU입니다. Mac GPU를 사용하려면 `.env`에 `WL_API_DEVICE=mps`를 지정하고 서버를 다시 시작하세요. 서버 한 프로세스가 영상 한 편씩 분석합니다.

## 브라우저에서 사용

1. [API 문서 열기](http://127.0.0.1:8000/docs) → **영상 분석 → MP4 한 편 분석** → **Try it out**을 누릅니다.
2. `video`에 MP4를 선택합니다. `near_side`는 카메라에 가까운 **선수의 왼쪽·오른쪽**, `facing`은 선수가 보는 **화면의 왼쪽·오른쪽**입니다. 각 값은 `left` 또는 `right`입니다.
3. 원판은 자동으로 보완합니다. 두 모델이 각자의 궤적을 추적하고, 베이스라인의 직접 검출과 시간 연결이 모두 비면 그 프레임에 CutMix 결과를 사용합니다. 수동 시점은 아는 것만 입력하세요. 첫 프레임은 0입니다.
4. **Execute**를 누릅니다. 완료 응답의 `summary_url`과 `files`는 같은 서버의 경로입니다. 예를 들어 `http://127.0.0.1:8000` 뒤에 `files["overlay.mp4"]` 값을 붙여 브라우저 주소창에서 열 수 있습니다. `frames.csv`는 다운로드하고, 캐치·피니시 관측이 있으면 결과 PNG도 열 수 있습니다.

| Swagger 메뉴 | 요청 | 용도 |
| --- | --- | --- |
| 영상 분석 | `POST /analyses` | MP4 한 편 제출. 분석 ID·수치·결과 링크 반환 |
| 영상 분석 | `GET /analyses/{analysis_id}` | 이전 분석의 요약과 링크 다시 열기 |
| 영상 분석 | `GET /analyses/{analysis_id}/files/{filename}` | 오버레이 MP4·프레임 CSV·생성된 그래프 PNG 열기 |
| 시점 검수 | `POST /analyses/{analysis_id}/pull-review` | ready 또는 transition을 수정해 두 구간의 평균속도와 뒤/앞 비율 재계산 |
| 시점 검수 | `POST /analyses/{analysis_id}/catch-to-finish` | catch와 finish를 선택해 어깨 기준 원판 위치와 체간 기울기 그래프 생성 |

프레임을 보면서 수정하려면 분석 응답의 `pull_review_url` 또는 `recovery_review_url`을 여세요. 두 화면에서 저장한 결과도 같은 분석 ID에 반영됩니다.

### 당기기 시점 제안과 검수

1. **POST /analyses**에 MP4와 촬영 방향을 입력합니다. ready·transition을 비우면 자동으로 찾은 시점으로 구간 속도와 뒤/앞 비율을 바로 계산합니다. 찾지 못한 시점은 빈칸이고, 그 시점이 필요한 수치는 산출 보류입니다.
2. 결과가 맞으면 그대로 사용합니다. 수정하려면 `pull_review_url`에서 해당 프레임 번호를 바꾸거나 **지금 보는 프레임 사용**을 누른 뒤 **수정한 시점으로 다시 계산**을 선택합니다.
3. 수정한 항목만 사용자 저장으로 표시합니다. 예를 들어 transition만 바꾸면 ready는 자동 적용으로 남습니다. Swagger에서도 **POST /analyses/{analysis_id}/pull-review**에 바꿀 항목만 보낼 수 있습니다.

### Swagger에서 속도와 체간 기울기 읽기

**Execute → Response body**에서 기본 코칭 수치를 읽습니다. 두 속도와 비율에는 drive·catch 입력이 필요하지 않습니다. 저장된 분석은 **GET /analyses/{analysis_id}**에서 확인합니다.

| 응답 필드 | 읽는 방법 |
| --- | --- |
| `lift_to_knee_speed_px_s` | 이륙부터 무릎 통과까지 원판 중심의 평균 수직속도(px/s). 위로 올라가면 양수입니다. |
| `trunk_change_deg` | 가까운 어깨와 골반을 이은 선이 이륙 때보다 무릎 통과 때 얼마나 기울었는지 나타냅니다. 음수면 몸통이 더 세워졌습니다. |
| `first_peak_frame` | transition 이후 두 번 연속 올라간 원판이 세 번 연속 내려가기 직전 프레임. 미확인 시 null. |
| `transition_to_first_peak_speed_px_s` | transition부터 첫 상승 최고점까지 원판 중심의 평균 수직속도(px/s). 하강을 확인한 세 프레임은 계산 시간에서 제외합니다. |
| `pull_speed_ratio` | 후반 평균 수직속도 ÷ 전반 평균 수직속도. `pull_speed_late_over_early`와 같은 값입니다. |
| `pull_speed_late_over_early` · `pull_speed_verdict` | 뒤 속도 ÷ 앞 속도. 0.90 미만은 느림, 0.90~1.10은 비슷, 1.10 초과는 빠름입니다. 양쪽 상승 속도를 비교할 수 없으면 판정을 보류합니다. |
| `pull_speed_evaluated_shifts` | transition 또는 첫 상승 최고점 하나만 ±1프레임 옮긴 네 조건 중 계산 가능한 수. 예전 분석에 이 검사가 없으면 `null`입니다. |
| `pull_speed_range` | 판정이 바뀔 때만 응답에 포함합니다. 입력한 이륙을 고정하고, 기준과 계산 가능한 변경에서 나온 두 평균속도와 뒤/앞 속도 비율의 최솟값·최댓값을 보여줍니다. |

API 0.2에서 `pull_speed_ratio`는 **뒤/앞**으로 바뀌었습니다. 이전 응답은 **앞/뒤**였고 후반도 바 접촉에서 끝났습니다. 기존 클라이언트는 후반 속도 필드를 `knee_to_contact_speed_px_s`에서 `transition_to_first_peak_speed_px_s`로 바꿔야 합니다. 예전 분석을 조회하면 저장된 궤적과 원본 시각으로 새 정의의 값을 다시 계산합니다.

첫 상승이 끝나기 전에 영상이 끝나거나 원판 좌표가 끊기거나 박스가 화면 경계에 닿으면 후반 속도와 뒤/앞 비율은 `null`입니다. 측정 가능한 전반 속도는 표시합니다.

응답의 `plate_mode=cutmix`는 자동 보완을 켰다는 뜻입니다. `selected_model_counts.cutmix`는 실제로 보조 좌표를 채택한 프레임 수입니다. 베이스라인 단독 비교는 CLI의 `--plate-mode single`로 재현할 수 있습니다.

`plate_counts`는 직접 검출·시간 연결·좌표 누락을 셉니다. 새 영상은 수동 정답이 없어 정확도·오탐률을 채점할 수 없습니다. `lift_to_knee_rise_px`는 이륙→무릎 통과, `knee_to_contact_rise_px`는 무릎 통과→접촉 상승량입니다. 시점이나 원판 좌표가 부족해 계산할 수 없으면 값은 `null`입니다. 후자의 측정 출처와 보류 이유도 함께 반환합니다.

### 접촉부터 원판 최고점까지

`drive`와 `catch`를 입력하면 Swagger 응답의 `drive_to_peak`와 로컬 `summary.json`의 `coaching.drive_to_peak`에서 같은 지표를 볼 수 있습니다. 접촉 프레임부터 캐치 바로 전까지 추적한 원판 중심이 가장 높은 첫 프레임이 `peak_frame`입니다. `rise_px`는 접촉 이후 더 올라간 높이이고, `mean_speed_px_s`는 이 높이를 원본 경과 시간 `elapsed_s`로 나눈 값입니다.

`speed_range_px_s`는 종료점을 최고점의 직전·해당·직후로 바꿔 계산한 세 평균속도의 최솟값과 최댓값입니다. 양옆을 모두 계산할 수 없으면 범위는 `null`이고 `range_reason`에 이유가 표시됩니다. 캐치 시점이 없으면 `status`는 ‘산출 보류’입니다. `missing_frames`로 구간 중 원판 관측이 빠진 장수를 확인할 수 있습니다. 캐치를 다시 판독해 저장하면 API는 그 시점으로 다시 계산합니다.

## 분석 후 캐치·피니시 그래프 만들기

1. 완료 응답의 `recovery_review_url`을 같은 서버에서 엽니다. 이전 분석도 ID로 요약을 다시 조회하면 이 경로가 표시됩니다.
2. 오버레이를 멈추고 캐치와 피니시에서 각각 **현재 프레임 선택**을 누릅니다. 이전·다음 프레임 버튼으로 한 장씩 이동하거나 화면의 Frame 번호를 직접 입력할 수 있습니다.
3. **그래프 만들기**를 누르면 구간 내 측정 장수와 그래프가 나타납니다. **그래프 PNG 저장**으로 내려받습니다. 다시 열면 마지막으로 저장한 구간이 표시됩니다.

위 그래프는 카메라에 가까운 쪽 어깨를 기준으로 원판 박스 중심이 얼마나 앞(+)이나 뒤(−)에 있는지 픽셀로 보여줍니다. 아래 그래프는 어깨와 골반을 연결한 선의 수직 기준 기울기입니다. 측정값이 없는 구간은 선이 끊기며, 두 지표가 모두 비면 이유를 표시합니다. 그래프의 한글을 표시하려면 실행 환경에 한글 글꼴이 있어야 합니다. Mac은 Apple SD Gothic Neo, Linux는 Noto Sans CJK를 사용할 수 있습니다.

사후 선택은 그래프용 판독으로 저장합니다. `manual_events`와 원래 오버레이·CSV는 업로드 당시의 기록이며, 현재 그래프에 쓰인 두 시점은 응답의 `catch_to_finish`에서 확인합니다.

## c04 재현

다른 터미널에서 프로젝트 루트를 열고 실행합니다.

```bash
curl -sS http://127.0.0.1:8000/analyses \
  -F 'video=@data/raw/videos/c04_sn_f_01.mp4' \
  -F near_side=left -F facing=left \
  -F lift_off=11 -F knee_pass=27 -F drive=43 -F catch=78 -F finish=107
```

원본 업로드의 임시 사본은 요청 종료 시 정리됩니다. 결과는 `WL_OUTPUT_DIR/api/<분석 ID>/`에 저장되므로 서버를 다시 시작해도 같은 ID로 조회할 수 있습니다. API는 사용자가 올린 원본과 모델 경로가 포함된 로컬 `summary.json`을 다운로드 목록에서 제외합니다.

## 자동 보완 기본값 확인

모드 항목을 보내지 않고 두 영상을 다시 제출했습니다. a03은 전체 122프레임에서 베이스라인 107장, CutMix 8장, 좌표 누락 7장이었습니다. 동작 중 수동 박스가 있는 40장에서는 기존 단독 정탐 27장을 유지하고 8장을 추가로 복구했습니다. c04는 116장 모두 베이스라인을 채택해 CutMix 채택이 0장이었고, 이륙→무릎 통과 상승량은 +160.514px였습니다.

## 초기 API 비교 기록 (Mac CPU)

| HTTP로 제출한 영상 | 결과 |
| --- | --- |
| c04 베이스라인 단독, 수동 시점 5개 | 116장 모두 직접 검출. 이륙 11→무릎 통과 27 상승량 +160.514px. 무릎 통과→접촉은 코사인으로 +215.43px |
| a03 CutMix, 무릎 통과·접촉 지정 | 전체 122장. 동작 중 수동 박스 40장에서 단독 모델 27장, API 보조 모드 35장 정탐. 4~6번과 10~14번 복구 |
| c04 베이스라인 단독, 시점 생략 | 116프레임 오버레이와 CSV 생성. 구간 상승량은 `null` |

시점을 지정한 두 영상의 CSV와 디코딩한 오버레이 238프레임을 같은 입력의 CLI 결과와 대조해 일치를 확인했습니다. c04의 캐치→피니시 그래프도 같은 픽셀로 저장됐습니다. 이 Mac의 로컬 HTTP에서 업로드 시작부터 요약 재조회 및 생성된 파일 다운로드까지 c04는 12.26초, a03은 13.59초였습니다. 각각 1회 측정한 시연 기록입니다.
