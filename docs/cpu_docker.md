# Mac에서 CPU Docker로 영상 분석하기

Mac의 Docker Desktop에서 Linux CPU용 FastAPI를 실행합니다. Python과 FFmpeg는 이미지에 들어 있고, 가중치는 실행할 때 연결합니다. 프로젝트 루트에서 다음 명령을 실행하세요.

```bash
docker compose up --build -d api
```

[로컬 분석 화면](http://127.0.0.1:8001/docs)에서 MP4와 촬영 방향을 제출합니다. 원본은 Mac에서 컨테이너의 임시 폴더로 전송되고 요청이 끝나면 임시 사본이 정리됩니다. 한 편의 분석이 끝나면 오버레이 MP4, 프레임별 CSV와 요약을 열 수 있습니다. 캐치·피니시를 사후 선택하면 같은 CSV에서 그래프를 만듭니다.

| Mac 폴더 | 컨테이너 위치 | 용도 |
| --- | --- | --- |
| `./models/pytorch` | `/models/pytorch` | 읽기 전용. `plate_baseline.pt`, `plate_cutmix.pt`, `yolo26n-pose.pt`를 둡니다. 이전 무릎 통과→접촉 상승량 비교를 재현할 때만 `plate_cosine.pt`를 추가합니다. |
| `./outputs/docker_analysis` | `/results` | 분석별 결과를 보관해 컨테이너를 다시 만들어도 같은 ID로 조회합니다. |

가중치 폴더, 결과 폴더, Mac 쪽 포트는 각각 `WL_CPU_WEIGHTS_DIR`, `WL_CPU_RESULTS_DIR`, `WL_CPU_PORT`로 바꿀 수 있습니다. 다음은 다른 로컬 폴더를 쓰는 예입니다.

```bash
WL_CPU_WEIGHTS_DIR=./models/cpu WL_CPU_RESULTS_DIR=./outputs/cpu docker compose up -d api
```

실행 중인 서버는 `docker compose logs api`로 확인하고 `docker compose down`으로 종료합니다. 빌드에 전달하는 파일을 `.dockerignore`에서 지정합니다. 선수 영상·가중치·로컬 설정은 Mac에 보관합니다.

## 기존 결과와 대조하기

Mac에서 같은 가중치·시점·촬영 방향으로 만든 API 결과와 수동 원판 박스가 준비돼 있어야 합니다. 기존 실험 환경과 호스트의 `ffprobe`를 사용해 세 영상을 실제 HTTP로 제출합니다.

```bash
PYTHONPATH=. .venv/bin/python deploy/cpu/verify.py
```

기본 참조 폴더는 `outputs/file_analysis/api`입니다. `--references`, `--results`, `--port`로 바꿀 수 있습니다. 검증 결과는 로컬 결과 폴더의 `comparison.json`에 저장됩니다. 프레임별 검출 상태와 모델 선택, 수동 박스와의 IoU 0.50 이상 여부, H.264 영상의 디코딩 장수를 확인합니다. b00에서는 기존에 판독한 캐치와 피니시를 분석 후 다시 제출해 거리·체간 기울기의 결측 프레임과 수치까지 대조합니다. 수치 비교 허용 오차는 거리 0.1px, 각도 0.1°입니다.

## 같은 가중치에서 그래프가 달라진 원인

첫 Linux 이미지에서 b00의 캐치 121번부터 피니시 227번까지 어깨를 기준으로 거리를 계산할 수 있는 프레임은 49장이었습니다. Mac에서는 65장이었습니다. 원판 검출은 양쪽 모두 254프레임에 성공해 원판 정탐 수만 봐서는 차이가 드러나지 않았습니다.

같은 압축 영상에서 디코더가 내놓은 픽셀과 모델에 넣기 직전의 픽셀을 따로 비교했습니다. b00은 10비트 HEVC로 저장된 HDR 영상입니다. 처음 비교한 세 프레임에서 디코딩한 채널 값의 평균 절대 차이가 약 30이었습니다(0~255 기준). 디코딩을 맞춘 중간 이미지에서는 64장이 남았습니다. 195번 원본 픽셀은 같았지만 리사이즈 결과가 달랐고, 두 번째 사람 후보의 신뢰도가 0.2646이 되면서 수행자를 한 명으로 정할 수 없어 자세 측정이 보류됐습니다.

최종 CPU 이미지에서는 PyAV 14.2.0과 bicubic 색차 변환으로 영상을 읽고 OpenCV 4.14.0.94로 모델 입력 크기에 맞춥니다. 원판과 수행자의 모델 가중치, 검출 기준, 시간 연결 규칙은 기존 실험과 같습니다. 입력 단계별 비교에서는 b00 130·154·195번의 원본 픽셀과 리사이즈 배열이 모두 Mac과 일치했습니다. 오버레이 H.264 파일은 OpenCV 인코더를 열 수 없으면 FFmpeg의 libx264로 저장합니다.

API에서는 한 번에 영상 한 편을 디코딩합니다. 디코더 스레드 수를 1로 고정하고 FFmpeg 로그는 표준 오류로 보냅니다. Docker 이미지에서 `PYAV_LOGGING=off`로 설정해 FFmpeg 스레드가 Python 로그 콜백을 기다리는 상황을 피합니다. [PyAV 로깅 문서](https://pyav.org/docs/stable/api/utils.html#disabling-logging)

## Mac CPU와 Docker CPU 결과

| 영상 | 같은 영상의 기존 Mac CPU 결과 | 최종 Linux ARM64 컨테이너 결과 | 업로드부터 응답까지 |
| --- | --- | --- | ---: |
| a03 | 동작 중 35/40 정탐, CutMix 8장 복구 | 같은 4~6번과 10~14번 복구. 전체 122장에서 채택 모델과 검출 상태 일치 | 34.91초 |
| c04 | 동작 중 69/69 정탐, 이륙→무릎 통과 +160.514px | 69/69, +160.514px. 무릎 통과→접촉 코사인 상승량 +215.430px | 33.25초 |
| b00 | 캐치 121→피니시 227, 거리와 각도 각각 65/107장 측정 | 각각 65/107장과 65/107장. 결측 프레임 일치 | 67.65초 |

b00의 같은 프레임에서 Mac과 컨테이너 간 최대 차이는 원판–어깨 수평 거리 0.00016px, 체간 기울기 0.00007°였습니다. 세 편의 H.264 오버레이를 끝까지 디코딩했고 원본 표시 시각과 CSV 프레임 번호를 확인했습니다. 컨테이너를 다시 만든 뒤 세 분석 ID로 요약과 오버레이·CSV를 다시 열었으며 b00의 선택 구간과 PNG도 보존됐습니다.

시간은 한 Mac에서 영상별로 한 번씩 측정한 HTTP 업로드부터 분석 응답까지의 경과 시간입니다. b00의 그래프를 사후 생성하는 요청은 별도입니다.
