# 스내치 분석을 빠르게 만들면서 무엇을 보존했나

측면 영상에서 원판을 추적해 수직 이동량을 구하고, 가까운 어깨와 골반으로 체간 기울기를 표시한다. 같은 검증 선수에서 실행 엔진을 바꾼 뒤 원판을 새로 놓치는지, 궤적과 관절 좌표가 얼마나 달라지는지, 한 편의 결과를 저장하는 데 몇 초가 걸리는지를 확인했다.

## 원판 모델의 속도와 검출 정확도

Apple M2 CPU, FP32, 배치 1, 긴 변 640(실제 입력 640×384). 같은 사진의 전처리 텐서, 외부 NMS와 좌표 복원, Ultralytics 채점 방식을 공유했다. 원판 mAP는 학습 8명과 분리한 검증 6명 39장의 모든 NMS 후 후보로 계산했다. 운영 시간 연결을 넣기 전의 검출기 평가다.

| 원판 모델 | mAP50 | mAP50–95 | 모델 지연 p50 / p95 | 모델 처리량 |
| --- | ---: | ---: | ---: | ---: |
| PyTorch FP32 | 0.989717 | 0.925418 | 28.60 / 36.98 ms | 33.44 fps |
| ONNX Runtime FP32 | 0.989717 | 0.925418 | 18.81 / 22.91 ms | 50.82 fps |

- 55번에서 원본 가중치와 46번 ONNX의 체크섬을 확인하고 품질을 다시 채점했다. IoU 0.50부터 0.95까지 10개 기준 모두 AP가 같았다. 직접 검출 기준 0.10에서는 둘 다 TP 38, FP 0, FN 1이었다. 같은 a03 이륙 2번을 놓쳤다. IoU 0.95의 AP는 두 엔진 모두 0.782984였다. 검증 사진에는 모두 원판이 있어 원판 없는 새 선수 영상의 오탐률은 이 수치로 추정할 수 없다.
- 시간은 같은 그래프를 쓴 46번의 원본 영상 6편 687프레임에서 읽었다. 두 엔진에 4스레드를 사용하고 영상별로 각각 10회 예열했다. 모델 실행 중앙값은 34.2% 줄었다. 처리량은 687을 누적 추론 시간(초)으로 나눈 값이다. 별도 실행에서도 PyTorch 38.52 ms, ONNX 23.01 ms로 방향은 같았고 절대 시간은 달랐다. [55번 재현 노트북](../notebooks/experiments/55_runtime_quality.ipynb) · [46번 조건과 좌표 비교](onnx_plate_parity.md)

## 영상에 표시하는 값도 보존됐나

- 원판은 687장에서 두 엔진 모두 직접 검출 662장, 시간 연결 5장, 출력 없음 20장이었다. 출력이 없는 장면 전체에 수동 정답이 있는 것은 아니다. 수동 박스를 확인한 무릎 통과~접촉 56장에서는 56장 모두 두 엔진의 선택 박스가 IoU 0.50 이상이었다. c04 이륙→무릎 통과 원판 중심의 수직 상승량은 모두 +160.51 px였다. [원판 비교](onnx_plate_parity.md)
- 원본 YOLO26n-pose는 이륙·무릎 통과 12장에서 가까운 쪽 관절 48개의 표시·보류 판정이 일치했다. 표시된 점의 엔진 간 최대 거리는 0.000440 px, 선수별 체간 변화량의 최대 차이는 0.0000553°였다. 직접 확인한 수동 어깨 12점까지의 평균 오차는 두 엔진 모두 10.47 px였다. 골반 12점은 옷에 가린 소켓을 추정해 해부학적 각도 오차를 채점할 수 없었다. [관절과 체간 각도 비교](onnx_pose_parity.md)

## 실제 병목과 선택

c04 116프레임에서 디코딩부터 두 모델의 좌표 복원까지의 중앙값은 PyTorch CPU 69.72 ms, ONNX CPU 46.95 ms, PyTorch MPS 22.29 ms였다. 4스레드 ONNX CPU의 별도 측정에서 원판 추론 19.43 ms와 자세 추론 24.00 ms가 대부분을 차지했고 NMS·좌표 복원은 0.75 ms였다. 각 단계의 중앙값은 각자 측정한 값이다. [Mac 장치 비교](mac_mps_latency.md) · [단계별 시간](onnx_cpu_latency.md)

Mac MPS에서는 두 모델이 같은 원본을 한 번만 읽도록 바꿨다. c04에서 명령 시작부터 완성된 H.264 영상·CSV·JSON 저장과 프로세스 종료까지 세 블록의 중앙값이 **11.30초 → 8.96초(20.7% 단축)**가 됐다. 완성 영상 처리량은 약 **10.26 → 12.94 fps**였다. 디코딩해 대조한 116장의 출력 픽셀, 판정과 저장 좌표가 모두 같았다. 추가 반복에서도 한 번 읽기가 더 빨랐다(15.02초 → 12.65초). 두 실행 모두 이 한 영상의 측정이다. [한 번 읽기 실험](overlay_read_comparison.md)

원판 입력을 512로 낮추면 네 차례 반복한 명령 전체 중앙값이 c04에서 8.74초 → 8.58초였지만 b02에서는 7.90초 → 7.99초였다. b02의 수동 이륙→무릎 통과 상승량(+252.00 px)을 작게 잡은 정도도 3.81 px에서 10.07 px로 커졌다. Mac에서는 두 모델의 입력 640과 한 번 읽기를 유지한다. [입력 크기 비교](plate_input_size_mps.md)

## NVIDIA GPU에서 남은 판단

같은 GPU에서 PyTorch CUDA FP32, ONNX Runtime CUDA FP32, TensorRT FP32를 비교해 엔진 효과를 먼저 측정한다. 다음으로 TensorRT FP32와 FP16을 비교해 정밀도를 낮췄을 때의 차이를 구한다. 가중치, 배치 1, 입력 형태, NMS, 시간 연결과 수행자 보류 규칙을 고정하고 실행 정밀도·TF32 설정, GPU 모델·소프트웨어 버전을 기록한다.

- 합성 입력으로는 엔진 생성과 첫 실행을 따로 재고, 예열 후 동기화한 추론 p50·p95와 처리량을 비교할 수 있다. 실제 입력 사용 범위가 결정되면 같은 39장으로 mAP 차이를 %p로 보고, 동작 중 원판 정탐을 새로 얻거나 잃은 프레임, 수동 허브의 세로 오차·상승량, 관절 위치·표시·체간 변화 방향을 대조한다. 누락된 장면을 좌표 오차 집계에서 별도 표시한다. [NVIDIA 성능 측정](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)
- 한 편의 처리 시간은 디코딩, 전처리·데이터 전송, 두 모델 추론, NMS·좌표 복원, 시간 연결, 오버레이·인코딩·저장까지 측정한다. 같은 세로 영상과 출력 규격에서 반복한 전체 초와 실제 처리 fps를 기재한다. 빠른 엔진이 동작 중 미탐이나 상승량·각도의 방향을 바꿨다면 그 사례와 손익을 함께 보고 채택을 결정한다.
- FP16은 부동소수점 정밀도를 낮추는 비교다. INT8 학습 후 양자화는 FP16 이후에도 추론이 병목이고 대표적인 **학습 선수 측** 보정 자료를 확보했을 때 진행한다. 검증 6명은 보정에 사용하지 않는다. TensorRT의 지연과 품질은 아직 미측정이다. [NVIDIA 양자화 안내](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/inference-library/work-quantized-types.html)
